# Практическая работа № 6 — Синхронизация

Вариант B. Python 3, только стандартная библиотека.

## Что реализовано

| Файл | Назначение |
|---|---|
| `race.py` | Счётчик без мьютекса: контролируемая гонка, потеря обновлений |
| `race_fixed.py` | Счётчик с `threading.Lock` |
| `pc_fixed.py` | Кольцевой буфер на 5 ячеек: два семафора + мьютекс или Condition + мьютекс |
| `barrier.py` | Собственный повторно используемый барьер на Condition для 4 потоков и 3 фаз |
| `condition_if_bug.py` | Воспроизводимая ошибка `if` вместо `while` и её исправление |
| `lost_wakeup.py` | Потерянное уведомление из-за разрыва между проверкой условия и `wait`, исправление |
| `INSTRUCTIONS.md` | Инструкция для Mac → SSH → Ubuntu → GitHub |

`queue.Queue` не используется. Буфер хранится в фиксированном списке с индексами
`head`, `tail` и счётчиком `count`. Работают 3 производителя и 2 потребителя;
в каждом запуске обрабатываются ровно 1000 элементов с ID от 0 до 999.
Два дополнительных маркера STOP служат только для завершения потребителей
и не входят в 1000 элементов.

## Запуск

Из корня проекта:

```bash
python3 race.py
python3 race_fixed.py
python3 pc_fixed.py --mode sem
python3 pc_fixed.py --mode cond
python3 barrier.py
python3 condition_if_bug.py --mode if
python3 condition_if_bug.py --mode while
python3 lost_wakeup.py
python3 lost_wakeup.py --fixed
```

Повторная проверка обоих вариантов буфера:

```bash
python3 pc_fixed.py --mode sem --runs 20
python3 pc_fixed.py --mode cond --runs 20
```

Зависимости через pip и виртуальное окружение не требуются.

## Проверки корректности

При каждой операции буфера проверяются:

- `0 <= count <= 5`;
- допустимость индексов;
- `tail == (head + count) % 5`;
- соответствие занятых ячеек размеру и расположению кольцевого буфера;
- отсутствие вставки в полный буфер и извлечения из пустого.

Производители и потребители ведут защищённые мьютексом счётчики ID.
Повторный ID немедленно регистрируется как нарушение. После завершения
потоков оба Counter сравниваются с `Counter(range(1000))`: проверяются
все ID и кратность ровно 1, а не только общая сумма. Итоговый буфер должен
быть пуст. Ошибки рабочих потоков передаются главному потоку, есть
тайм-ауты ожидания и завершения. Проверки используют исключения,
а не `assert`, поэтому не отключаются при запуске с `-O`.

У барьера проверяется, что каждый из четырёх потоков завершил каждую фазу,
следующая фаза не началась до завершения предыдущей всеми потоками,
а итоговое поколение барьера равно 3.

Логи создаются в `logs/` при запуске. Каждый повторный запуск программы
перезаписывает её лог. `--runs 20` сохраняет все 20 повторений в одном логе.
Каталог `results/` можно создать для сохранения вывода через `tee`.

## Как работает синхронизация

В `race.py` четыре потока читают одно старое значение, затем записывают
одно и то же новое. Барьеры задают воспроизводимое чередование, но не
защищают операцию изменения счётчика. Поэтому за раунд значение растёт
на 1 вместо 4. В `race_fixed.py` чтение и запись выполняются под одним
мьютексом. Демонстрационные барьеры убраны: ожидание других потоков
внутри удерживаемого мьютекса привело бы к взаимной блокировке.

Для семафоров `empty=5` считает свободные места, `full=0` — доступные
элементы. Производитель резервирует свободное место, изменяет буфер
под мьютексом, затем публикует элемент через `full.release()`.
Потребитель резервирует доступный элемент, извлекает его под мьютексом,
затем возвращает свободное место через `empty.release()`.
Ожидание семафора происходит до захвата мьютекса буфера.
Счётчики семафоров в переходных состояниях могут учитывать зарезервированные
места/элементы: не следует требовать `empty + full == 5` в произвольный момент.

В варианте Condition производитель ждёт, пока буфер полон, потребитель —
пока он пуст. `wait()` временно освобождает общий мьютекс и возвращается
с вновь захваченным мьютексом. Условие проверяется в `while`.
Поскольку одна Condition обслуживает производителей и потребителей,
после изменения состояния используется `notify_all()`: каждый разбуженный
поток самостоятельно проверяет своё условие. Работа с данными и задержки
выполняются вне мьютекса буфера.

Барьер хранит число прибывших потоков и номер поколения. Четвёртый поток
обнуляет число прибывших, увеличивает поколение и будит остальных.
Остальные ждут смены именно своего поколения, поэтому барьер можно
повторно использовать в трёх фазах. Готовый `threading.Barrier` в этом
файле не применяется.

## Почему if вместо while ломается

1. Два потребителя видят пустой буфер и вызывают `wait()`.
2. Производитель добавляет один элемент и вызывает `notify_all()`.
3. Первый потребитель захватывает мьютекс и забирает элемент.
4. Второй получает мьютекс, возвращается из `wait()` и продолжает работу.
5. С `if` проверки больше нет: попытка чтения из пустого буфера.
6. С `while` второй потребитель вновь проверяет условие и ждёт.

События Event в демонстрации задают чередование, а не реализуют буфер.
В исправленном демонстрационном режиме главный поток затем объявляет
закрытие буфера, чтобы оставшийся потребитель корректно завершился.

Точный термин для этого сбоя — отсутствие повторной проверки условия
после пробуждения. Это отличается от настоящего потерянного уведомления:
потребитель проверяет условие, отпускает мьютекс; производитель меняет
состояние и вызывает `notify()`; потребитель только потом вызывает `wait()`.
Condition не запоминает уведомления для будущих ожидающих.
`lost_wakeup.py` воспроизводит именно это чередование; тайм-аут 0,3 с
нужен, чтобы демонстрация не зависла. Исправление объединяет проверку
с `while ... wait()` под одним общим мьютексом.

## Контрольные вопросы

**1. Семафор со значением 1 и мьютекс.**
Мьютекс применяется для взаимного исключения при доступе к данным.
Семафор ведёт счёт разрешений и может использоваться для передачи
сигнала между потоками. `Semaphore(1)` после лишнего `release()` может
стать равным 2 и перестать обеспечивать исключение; у `Lock` такой
счётчик отсутствует. Важная особенность Python: обычный `threading.Lock`
не закрепляет владельца, другой поток может его освободить; `RLock`
отслеживает владельца. Поэтому отличие через владельца нельзя без
оговорки переносить на `threading.Lock` из других языков.

**2. Почему Condition нужна вместе с мьютексом.**
Общий мьютекс защищает состояние и связывает проверку условия с
постановкой на ожидание. Производитель не может изменить состояние
между проверкой и атомарным переходом в ожидание. После пробуждения
мьютекс вновь захвачен, но условие всё равно необходимо перепроверить.
В Python вызов `wait()`/`notify()` без удержания соответствующего
мьютекса вызывает `RuntimeError`.

## Вывод

Состояние гонки устраняется защитой всей операции read-modify-write.
Оба варианта производителя–потребителя ограничивают буфер пятью
ячейками и проверяют однократное потребление каждого ID.
Барьер синхронизирует границы трёх фаз четырёх потоков.
Condition требует общего мьютекса и повторной проверки условия в цикле.
